最近在 Proxmox 的 LXC 容器裡設定 Tailscale 時，遇到一個一開始很像 Tailscale 壞掉的問題。

目標其實很單純：讓 LXC 可以透過 Tailscale 從外部裝置連進來。結果測下去才發現，內網 SSH 看起來可以用，外部卻打不進來；`tailscale status` 一度顯示裝置離線，`tailscale netcheck` 也顯示 UDP 不通、DERP 不可用。

一開始看起來像是 Tailscale key、ACL 或 Tailscale SSH 的問題，但最後真正的關鍵不是 Tailscale 本身，而是 <mark className="marker-yellow">Proxmox LXC 的網路與防火牆設定沒有完整對上</mark>。

這篇是一次排查紀錄，也順便整理之後遇到類似問題時比較穩的檢查順序。

## 一開始看到的現象

最初的狀況大概是這樣：

- LXC 容器在內網裡有拿到 IP。
- 容器可以連到 Proxmox 宿主機。
- 從外部透過 Tailscale 連進來不穩定。
- `tailscale status` 顯示裝置離線。
- `tailscale netcheck` 顯示 UDP 不通、IPv4 沒有正常偵測到。
- 後來網路恢復後，SSH 又變成 `Permission denied (publickey)`。

這幾個現象混在一起，很容易誤判成「Tailscale key 過期」、「Tailscale SSH 沒設定好」，或是「Tailscale 本身壞掉」。

但實際上，這幾件事在不同層級：**網路層、Tailscale 層、SSH 認證層**。如果一開始沒有拆開看，就會一直在錯的地方繞圈。

## 第一個誤判：以為是 Tailscale key 過期

因為裝置看起來離線，我一開始懷疑是不是 Tailscale 的 device key 過期。

後來確認後發現，這台裝置的 key expiry 已經是 disabled，也就是沒有因為金鑰過期被踢掉。所以這條線索可以先排除。

這一步其實很重要。<mark className="marker-pink">如果一開始就往 Tailscale 帳號、ACL、SSH policy 查，很容易花很多時間，但真正的問題根本不在那裡。</mark>

## 關鍵線索：LXC 連不到 gateway

真正把問題縮小的關鍵，是直接在 LXC 裡測基本網路。

我先測：

```bash
ping 192.168.1.10
```

這個可以通，代表 LXC 到 Proxmox 宿主機或橋接網路本身不是完全壞掉。

但接著測 gateway：

```bash
ping 192.168.1.1
```

這個卻不通。

這就很關鍵了。`192.168.1.1` 是 gateway，如果 LXC 連 gateway 都 ping 不到，代表問題不是單純的 Tailscale 連線問題，而是容器往外走的網路路徑本身就有狀況。

換句話說，Tailscale 需要對外連線才能正常工作。<mark className="marker-yellow">如果 LXC 自己連 gateway 都不穩，Tailscale 當然也會出現 UDP 不通、DERP 不可用、狀態離線之類的問題。</mark>

## 真正比較像的原因：LXC firewall 開了，但規則不完整

再往 Proxmox 設定看，宿主機本身的網路是正常的，`vmbr0` 和實體網卡也沒有明顯問題。宿主機可以正常連網，表示問題不是整台 Proxmox 對外斷線。

比較可疑的是 CT 1000 的網卡設定：

```text
net0: ...,firewall=1
```

也就是這個 LXC 的網卡有啟用 Proxmox firewall。

啟用 firewall 本身不是問題，真正危險的是：**只開了 `firewall=1`，但 CT 層級沒有把 inbound / outbound 的策略和規則設計完整**。

當時看到的狀況是，CT 的 firewall 規則主要只有 SSH 的 inbound accept，沒有看到完整的 outbound 放行設計。因此比較合理的推測是：

> LXC 的網路介面開了 firewall，但 CT 層級的防火牆規則不完整，導致容器往外連線時被擋住或不穩定。

這也解釋了為什麼 Tailscale 會一度看起來壞掉。它不是自己壞掉，而是底下的 LXC 出站網路就不正常。

## unprivileged LXC 裡的 TUN 條件

另一個要注意的點是，這台 LXC 是 unprivileged container。

Tailscale 要在 unprivileged LXC 裡正常跑，不能只安裝套件就好，還需要讓容器可以使用 `/dev/net/tun`。如果沒有 TUN 裝置，Tailscale 可能會出現服務有跑，但實際網路功能不完整的情況。

CT 設定裡需要確認類似這幾行：

```text
unprivileged: 1
lxc.cgroup2.devices.allow: c 10:200 rwm
lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file
```

| 設定 | 用途 |
|---|---|
| `unprivileged: 1` | 表示這是非特權容器，安全性較高，但某些系統資源需要額外開放 |
| `lxc.cgroup2.devices.allow: c 10:200 rwm` | 允許容器存取 TUN 裝置需要的 device 權限 |
| `lxc.mount.entry: /dev/net/tun ...` | 把宿主機的 TUN 裝置掛進容器裡 |

這不是這次唯一的問題，但它是 Tailscale 能不能在 LXC 裡穩定運作的基礎。

## 最後為什麼變成 SSH publickey 錯誤？

後來 Tailscale 狀態恢復後，我再用 SSH 連：

```bash
ssh root@100.71.162.57
```

結果出現：

```text
Permission denied (publickey).
```

這其實是好消息，因為它代表網路層已經通了。

如果網路不通，通常會是 timeout、no route to host、connection refused 之類的錯誤。但現在已經進到 SSH 的金鑰驗證階段，代表：

- Tailscale IP 可以連到。
- SSH server 有回應。
- 問題已經不是網路層。
- 剩下的是 SSH key 沒有對上。

所以最後這個錯誤不是 Tailscale 壞掉，而是 OpenSSH 不接受目前這把 key，或是 root 登入策略本來就有限制。

## 我最後整理出的排查順序

如果之後再遇到類似問題，我會照三層來拆。

### 1. 先確認 LXC 本身可以正常出網

```bash
ping 192.168.1.1
ping 8.8.8.8
```

如果連 gateway 或外部 IP 都不通，就不要急著查 Tailscale。這時候應該先回頭看 Proxmox bridge、LXC IP、gateway、DNS 和防火牆設定。

### 2. 再確認 Tailscale 能正常運作

```bash
tailscale status
tailscale netcheck
tailscale ping macbook
```

這幾個指令可以分別確認裝置狀態、對外連線能力，以及 tailnet 內的裝置能不能互相打通。

### 3. 最後才處理 SSH key

```bash
ssh root@100.71.162.57
ssh -v root@100.71.162.57
```

如果已經出現 `Permission denied (publickey)`，代表網路大致是通的。這時候就應該檢查目標主機的 `authorized_keys`、SSH 設定，以及目前本機到底拿哪一把 key 去登入。

## 實際可以怎麼修

先在 Proxmox 宿主機看 CT 1000 的設定：

```bash
pct config 1000
```

這裡主要看幾件事：

- `net0` 有沒有拿到正確的 IP。
- gateway 有沒有指到正確的路由器。
- `firewall=1` 是否有開啟。
- TUN 相關設定是否存在。

如果 `net0` 有開 `firewall=1`，就要去檢查 CT 1000 的 firewall options。

重點不是「不要開 firewall」，而是不要只開一半。比較穩的做法是：

- CT firewall 可以開。
- `policy_in` 依照需求設定，通常可以比較嚴格。
- `policy_out` 建議先確認是 `ACCEPT`，避免容器連 gateway、DNS、Tailscale 都被擋。
- SSH、Tailscale、內網服務再用明確規則控管。

<mark className="marker-orange">防火牆要管的是你想管的流量，而不是讓它不小心把容器所有 outbound 都卡住。</mark>

接著進入容器：

```bash
pct enter 1000
```

在容器裡照順序測：

```bash
ping 192.168.1.1
ping 8.8.8.8
tailscale status
tailscale netcheck
```

判斷方式很簡單：

- gateway 不通：問題還在 Proxmox bridge、LXC 網路或 firewall。
- gateway 通、外部 IP 不通：可能是路由或 NAT 問題。
- 外部 IP 通、網域不通：再往 DNS 查。
- Tailscale 通、SSH publickey 失敗：回到 SSH key 和登入策略。

## 指令快速整理

| 指令 | 英文原意 / 用途 |
|---|---|
| `ping` | 測試網路是否能到達目標主機，常用來確認基本連線 |
| `pct config` | Proxmox Container config，用來查看指定 LXC 的設定 |
| `pct enter` | Proxmox Container enter，用來進入指定 LXC 的 shell |
| `tailscale status` | 查看 Tailscale 裝置狀態，以及目前 tailnet 內的節點 |
| `tailscale netcheck` | 檢查 Tailscale 對外連線能力，例如 UDP、IPv4、DERP 狀態 |
| `tailscale ping` | 測試兩台 Tailscale 裝置之間是否能連通 |
| `ssh` | Secure Shell，用來透過加密連線登入遠端主機 |
| `ssh -v` | verbose 模式，顯示 SSH 嘗試使用哪些 key 和連線細節 |
| `pve-firewall status` | 查看 Proxmox firewall 服務狀態 |

## 這次學到的事

這次最大的收穫是：不要看到 Tailscale 顯示離線，就直接認定是 Tailscale 的問題。

Tailscale 本質上還是跑在原本的網路環境上。如果 LXC 自己的 gateway、firewall、TUN 裝置沒有設定好，Tailscale 也只能跟著出問題。

比較好的排查順序應該是：

1. 先確認 LXC 能不能連 gateway。
2. 再確認 LXC 能不能出網。
3. 再確認 Tailscale 的 `status` 和 `netcheck`。
4. 最後才處理 SSH key 或 Tailscale SSH 設定。

這樣一層一層拆，才不會把網路問題、防火牆問題、Tailscale 問題、SSH key 問題全部混在一起。

## 最終結論

這次問題可以濃縮成一句話：

> 我遇到的不是單純的 Tailscale 壞掉，而是 Proxmox LXC 的網路與防火牆設定讓容器一度無法穩定對外連線；等 Tailscale 連線恢復後，最後剩下的才是 SSH key 沒對上的問題。

之後如果要在 Proxmox LXC 裡跑 Tailscale，我會先確認三件事：

- LXC 的 gateway 和 outbound 網路是正常的。
- unprivileged LXC 有正確開放 `/dev/net/tun`。
- Proxmox firewall 如果要開，就要完整設定 policy 和規則，不要只開介面防火牆。

這次算是很典型的 Homelab 踩坑：表面上壞的是 Tailscale，實際上要修的是底下那層網路。
